# Proof

> **AI agents can act. Proof makes sure they actually did.**

Proof is a WebMCP-powered workspace where people and AI agents work together on tasks that matter. It keeps a shared view of what was requested, what was planned, and what actually happened — and it never calls a task complete until the final state has been checked.

The demo site is StayWell, a simulated hotel with real behavior: prices move with occupancy, competing demand lands between plan and approval, and rooms book up. You ask for something in plain language — *"Move my reservation to Friday, keep the same room, and stay under $300."* — and watch three things happen:

1. **Plan.** The ask becomes conditions the site itself can check: a date, a room, a price. Not vibes — predicates.
2. **Act.** The agent works out how to get there and prepares the change. Preparing is all it can do; applying it takes a person.
3. **Check.** After the change, the site re-reads its own state and compares it with what you asked. Only then is anything called done.

On the demo seed, the quote says $294. Competing demand lands, the site honestly charges $319 — and most software would report success. Proof reports the difference, shows exactly which condition broke, and puts the choice in your hands: undo it, keep it knowing the difference, or take a different room — with every option showing what it meets and what it breaks.

## Measured, not claimed

These numbers come from [evals/report.md](evals/report.md), generated by `pnpm evals` — 59 deterministic scenarios, including adversarial ones (an agent attempting to commit without approval, replaying an approval, re-injecting a stale plan, silently substituting a constraint-violating option):

| What | Measured |
| --- | ---: |
| Tasks tested | 59 |
| False completions | **0** |
| Agent commit attempts rejected | 8/8 (**100%**) |
| Unauthorised approval attempts rejected | 8/8 (**100%**) |
| Stale plans rejected | 2/2 (**100%**) |
| Changes committed (all human-approved) | 44 |
| Mismatches caught | 27 |

A caught mismatch is the product working, not failing: the world honestly disagreed with the plan, and Proof said so instead of calling the task complete. Every number above is reproducible from the seed — run `pnpm evals` and read the report it writes.

## Try it

```bash
pnpm install
pnpm dev        # http://localhost:3210
```

No account, no setup. The homepage's hero runs a real task through the real product — one click, and you watch the agent work, approve the change yourself, and see the check catch the price that moved.

Optional, to let the built-in agent use a language model instead of its deterministic playbook:

```bash
echo 'OPENAI_API_KEY=sk-...' > .env.local
```

With or without a key, the agent has no special privileges: it talks to the same HTTP API as a browser session, hits the same validation, and is refused by the same gates.

## Why WebMCP?

Only now, the technology.

Today, an agent "using" a website is guessing — reading screenshots, poking the DOM, hoping the button it found means what it thinks. WebMCP (`document.modelContext`) turns the page into a contract: the site itself declares what an agent can do, through structured tools with typed inputs and outputs that live in the page, gated by the browser's own lifecycle and permission model.

That contract is what makes Proof's guarantees possible:

- **The agent's reach is explicit.** Proof registers 13 tools — reads (task, quote, history), planning actions (set goal, stage a change), and recovery. Approving and committing are not among them; those buttons don't exist on the agent's side of the line, structurally, not by prompt. Even `verify_result` is absent from the tool set until after a change has been applied — and its verdict is computed by the site, never asserted by the agent.
- **State is shared, not narrated.** The agent and the human see the same task object — same constraints, same staged change, same revision — so "I changed your reservation" can't drift from what the task record says.
- **The site is the source of truth.** Verification isn't the agent reporting success; it's the site re-reading its own state after the change. The agent cannot argue with a `price_at_most` check. It either holds or it doesn't.

In short: WebMCP gives the agent honest hands. Proof is what you build when the hands are honest and you still want proof of the result.

## The pilot

Included agent so the demo works with no setup: a server-side pilot that plans and stages changes like any external agent would — plain HTTP to the app's own API, same-origin enforced, cookies forwarded, rate-limited per IP, capped globally per day. Without `OPENAI_API_KEY` it runs a deterministic scripted playbook; with a key it uses the OpenAI Responses API and falls back to the playbook on any failure. Either way it can quote, plan, and stage — never approve, commit, or verify. See [docs/architecture.md](docs/architecture.md).

## Repository

```text
src/
├── app/            # Next.js routes: pages + the HTTP API the agent surface mirrors
├── features/       # UI: workspace, task screen, mismatch & recovery, homepage
├── lib/
│   ├── proof/      # the domain: state machine, constraints, transactions,
│   │               # revisions, verifier, recovery, audit — engine-agnostic
│   ├── staywell/   # the simulated hotel: seeded demand schedule, yield pricing
│   ├── pilot/      # the built-in agent: scripted + model-backed, no privileges
│   └── http/       # route-level helpers: sessions, same-origin, task views
├── webmcp/         # the WebMCP surface: tool registry, schemas, adapter,
│                   # lifecycle gating, the withheld approval nonce, polyfill
└── components/     # shared UI primitives
evals/              # the harness, 59 scenarios, report.json / report.md
tests/              # unit and boundary tests (four-layer dependency enforced)
docs/               # architecture, webmcp, security, decisions, devpost, video
```

Layering is one-way and test-enforced: `webmcp/tools` may depend on `lib/proof`, which may depend on `lib/staywell` — never the reverse, and never a tool calling a transaction the human owns.

```bash
pnpm test         # 190 tests: domain, routes, pilot, boundaries
pnpm evals        # 59 scenarios; writes evals/report.{json,md}
pnpm typecheck
```
